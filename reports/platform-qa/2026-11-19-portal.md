## Findings

### 1. A sign-in ticket for one program opens every program  — high
Where: `functions/api/launch.js:121-127` (`makeTicket`), `:190-204`; the programs' `readPortalTicket` (e.g. Foundational-Training `worker.js:248-266`, `:3172-3182`)   Category: Disconnect (SSO)

What happens (plain): when a trainee opens a program, the Portal gives them a pass that is valid for five minutes. The pass
says who they are, but not which program it is for, and all six programs check passes with the same shared secret. So a pass
made for one program also works in the other five.

Steps:
1. Jane is an approved trainee in batch B111926. She has Portal access to **Lien Negotiation** only, or to no program at all.
   Any trainee can open a tool, because `launch.js:194` skips the access check for `?tool=`.
2. She opens `/api/launch?tool=kb` (or her LN card). The Portal answers with a redirect to `…?ticket=<payload>.<sig>`, where
   the payload is `{first, last, b, exp}` and names no program.
3. Within 5 minutes she opens `https://foundational-training.legalsupporthelp.workers.dev/?ticket=<same ticket>`.
4. FT's `/api/auth/portal` checks only the signature and the expiry. It signs her in and, at `worker.js:3172-3180`, writes
   `approved: true` on her FT trainee record. The comment there says: "The Portal's approval is the only trainee approval."

Result: Program Access on the Portal is the only gate, and this skips it. Two related points:
- Trainee tickets are not single-use at the programs. Only admin tickets go through `useTicketOnce`. A trainee ticket left
  in browser history or a forwarded link signs in as that trainee as many times as needed for 5 minutes.
- The comment at `launch.js:9-10` says the ticket is "only for the program it was made for". The code does not do that.

Fix: proposed, not applied because it changes the auth contract in seven repos. Have `makeTicket` add an audience,
`p: <topic key or tool id>`. Each program's `readPortalTicket` then refuses a ticket whose `p` is set and is not its own
topic key. Accept tickets with no `p` for one release, then require it. Each program audit should check that its Worker
does this.

### 2. The sign-in page's `?next=` can send a signed-in person to another website  — medium
Where: `functions/_middleware.js:49-51`   Category: Bug (front door)

What happens: the check `/^\/(?!\/)[^\\]*$/` blocks `//evil` and `/\evil`, but it lets through `/<TAB>/evil.com`. Browsers
remove tab characters from URLs, so a redirect to `/\t/evil.com` becomes `//evil.com`, which is another site. Steps: send a
signed-in trainee `https://cm-training-activity.pages.dev/trainee-login.html?next=%2F%09%2Fevil.example`. The middleware
answers `302 Location: /\t/evil.example` and the browser lands on `evil.example`. That page could be a copy of the sign-in
page that asks for their password again.
Verified: under `wrangler pages dev` with a valid session cookie, the response was
`302 Location=/<TAB>/example.org/phish`, and Chromium then requested `http://example.org/x`. The browser-side copy of this
check (`portal.js:164-165`) also compares the origin, so it is safe.
Fix: proposed, not applied because it is in the sign-in gate. Use the same rule as `portal.js`:
`const u = new URL(nxt || '/programs.html', request.url); const to = (/^\/(?![\/\\])/.test(nxt) && u.origin === new URL(request.url).origin) ? u.pathname + u.search : '/programs.html';`

### 3. Attendance "📋 Copy the sheet script" copies the Portal's home page  — medium
Where: `attendance.html:355-360` with `_redirects:10` (`/attendance-sync.gs / 302`)   Category: Misfire

What happens: the trainer setting up the attendance Google Sheet presses **📋 Copy the sheet script**. The page fetches
`/attendance-sync.gs`, but `_redirects` sends that file to `/`. The fetch follows the redirect and gets `index.html` with a
200, so `r.ok` is true and the clipboard gets the landing page's HTML. Pasting that into Apps Script fails with a syntax error,
and the "🕘 Platform Attendance" menu never appears. The fallback, `window.open('/attendance-sync.gs')`, is redirected to
the home page as well. README step 2 (`README.md:220`) tells trainers to use this button.
Verified: `wrangler pages dev` returns `302 → /` for `/attendance-sync.gs`.
Fix: proposed. The script contains no secret (the feed key is typed into the sheet), so either:
(a) serve it admin-only: add `/attendance-sync.gs` to `ADMIN_PAGES` in `_middleware.js` and drop the `_redirects` line, or
(b) serve its text from a small admin-only endpoint such as `GET /api/attendance-feed?script=1`. (a) is one line, but it
changes what is public, so it needs your OK.

### 5. Training Directory scrolls sideways on a phone while an access request is waiting  — low
Where: `programs.html:68`   Category: Bug (layout)

What happens: an admin opens the Training Directory on a phone (390px) while a trainee's access request is waiting. The
🙋 Access Requests table makes the whole page 547px wide and the program cards slide off the right edge. The cause:
`body` is a flex column (`styles.css:21`) and `.idx-wrap` has `margin: 0 auto`, so it sizes to its content. The table's own

request is ever waiting.
Fix: done in `236d222`. `.idx-wrap` now takes the full width, so the table scrolls inside its card. Width is 390 at 390px,
and unchanged at 700, 1360 and 2400px. At exactly 1000px the cards now fill the row instead of a centred 851px, which matches
every other width. Smoke and requests tests pass.

### 6. Trainees can't reach the Portal's own activities, lectures and grades  — medium
Where: `functions/_middleware.js:8` (`core` in `ADMIN_PAGES`); `core.html:147-260` (`view-trainee-*`); `app.js:2420-2490`   Category: Feature not working

What happens: `core.html` holds both the admin tools (Lesson Decks & Activities, Manage Lectures, Check & Release Grades) and
the trainee views that go with them (activities to submit, lectures, "My grades"). Since `core.html` became admin-only, a

trainee's **Details** view and **PDF** (`renderSubmissionAnswersHtml`, `app.js:1132-1137` and `:1174-1177`) compare each
answer against that missing key. If the trainee view is opened again, every answered objective question shows as
"✗ INCORRECT · Answer key:" with a blank key, including the correct ones.
Fix: proposed, as a decision. Either retire the Portal's activity and lecture tools, which also settles inventory items
1–3, or give trainees a page for them again. If they come back, `/api/submissions` GET should return a per-question
`correct: true/false` for graded submissions, and the view should use that instead of the answer key.

## Learning features (ranked)

### 1. "My progress" on each program card in the Training Directory  — effort M
**What:** each program card a trainee can open shows their own progress: days done out of the total, their average knowledge
check score, and "new feedback from your trainer" when there is some.
**Why it helps the trainee:** the Portal already gathers this for every trainee: day-by-day done and score, KC and practice
averages, and the trainer's daily feedback with sent/read state (`program-progress.js` `summarize`, `summarizeFeedback`). Only
admins ever see it, on `/progress.html`. A trainee who comes back to the Directory has no idea which program they are behind
in or that their trainer wrote to them.
**Where:** a new trainee-scoped mode of `/api/program-progress` (`?mine=1`) that reads only the caller's own
`<prefix>trainee:<id>` and `tfeedback`, using the program list in `_programs.js`. It renders in `cardFor` in `programs.html`.
**Dependencies:** no new KV keys. It reads one record per approved program, about 6 KV reads per page load. Fix finding 7
(day counts) first.

### 2. A simulator history that follows the trainee, with "try again" on the low scores  — effort S
**What:** the Simulators page lists all of the trainee's graded runs from any device, newest first. Each run under 70% has a
**Try again** button that reopens the same scenario.
**Why it helps the trainee:** today the history is per browser (finding 11), so the runs they most need to retry often aren't
there. The score chips already colour-code good, mid and low (`Sim.scoreChip`). Nothing yet turns a low score into a next step.
**Where:** `simulators/sim.js` history loader and `simulators.html`. It reuses `GET /api/sim-results`, whose `scenario`
column is already stored.
**Dependencies:** none.

### 3. Per-question "what you missed" after an objective quiz  — effort S (if the activities come back)
**What:** after an auto-graded activity, the trainee sees which questions they got wrong and the right answer, once the
submission is graded.
**Why it helps the trainee:** the Portal hides the key until submission, which is correct, but then shows nothing per question.
The view that tried to (finding 6) marks everything wrong, so a trainee can't learn from a miss.
**Where:** `/api/submissions` GET returns `correct` per question and the key for graded rows only; `renderSubmissionAnswersHtml`
in `app.js` uses it.
**Dependencies:** depends on the decision in finding 6.

### 4. "Practice today": the simulator that matches today's lesson  — effort M
**What:** the Directory and the Simulators page suggest the simulator that goes with the trainee's current day, for example
Calendaring on FT's "Calendaring & Appointment Setting" day or Records Requests on "Medical Records Specialist".
**Why it helps the trainee:** the lessons (`_attendance.js` `PROGRAMS[].days`) and the simulators
(`SIMULATORS.md`) are listed separately. A trainee has to know that a matching simulator exists and find it.
**Where:** a small lesson→simulator map next to `_attendance.js` `PROGRAMS`. The trainee's current day comes from the same
check-in record `_attendance.js` already reads (`<prefix>checkin:<date>:<id>`). It renders as a banner in `programs.html` /
`simulators.html`.
**Dependencies:** the map is content work for the program owner, a one-line pairing per lesson.

### 5. Spaced review of earlier days' weak knowledge checks  — effort M
**What:** when a trainee opens a program, a short "review from earlier" list links back to any earlier day whose knowledge
check score was under 80%.
**Why it helps the trainee:** `dayProgress[d].score` is stored for every day and is never used again once the day is done.
Without spaced review, what was missed on day 2 is still missed on day 9.
**Where:** computed from the same summary as feature 1. It is shown on the program card, and each program can show it on its
own home screen (the program audits can confirm where).
**Dependencies:** feature 1. Each program's deep-link format for "day n" needs confirming in its audit.

### 6. Count Lien Negotiator and Medsum & Demand practice in their own course  — effort M
**What:** simulator and call practice done for LN and MD is saved to those courses the way it already is for FT, CM, PD
and EA/PA.
**Why it helps the trainee:** `api/sim-results.js:15` (`COURSES`) and `launch.js:104` (`CALL_PROGRAMS`) list FT, CM, PD and
EA only. MD only counts text conversations (`call-results.js:75`). An LN or MD trainee's practice therefore never appears in
their course record or on the trainer's Trainee Monitoring row, so a trainer can't credit it or coach from it.
**Where:** `COURSES` / `CALL_PROGRAMS` / `PROGRAM_ALIASES` plus the program Workers' readers. This needs the LN and MD
audits to say whether those courses link to the simulators at all yet. LN's current `main` does not.
**Dependencies:** new `ln:` / `md:` simresult keys, which follow the existing `<prefix><kind>:<id>` contract, so Revoke
already covers them.

### 7. A shared glossary pop-up for legal terms across the simulators  — effort M
**What:** in any simulator, terms such as "PIP", "subrogation", "lien reduction" or "statute of limitations" are underlined,
and tapping one shows a one-line definition.
**Why it helps the trainee:** FT tests "Common Terms Used" as an assessment on day 2 (`ft-day-activities.js`), but the
simulators that use those terms days later never define them. `simulators/legal-rules.js` already holds rule text and could
hold the definitions as well.
**Where:** a `glossary.js` loaded by `simulators/sim.js`, the shared simulator shell, so every simulator gets it at once.
**Dependencies:** the definitions are content for the program owner.
