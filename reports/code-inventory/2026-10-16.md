## Needs a decision

**1. An all-objective activity is graded in raw points but shown as a percentage.** (high)
`functions/api/submissions.js:102-113`. `gradeAnswers` returns `autoScore = Σ q.points` (default
`points: 1`), written to both `auto_score` and `score` with `status='Graded'`. Ten one-point
questions all correct gives `score = 10`, and `app.js:2273` renders "10 / 100", `app.js:1254` and
`:2679` render "Graded · 10%", `api/progress.js:55` gives the trainee an average of 10,
`api/leaderboard.js:158` ranks them at 10, and the perfect-score celebration
(`app.js:2291`, `Number(s.score) === 100`) can never fire. A perfect submission reads as a 10% fail
to the trainee, the trainer and the leaderboard.
Two ways out, and they are not equivalent: normalise to a percentage of total points, which rewrites
how grades are stored and changes the admin's grade-box default at `app.js:1114`; or change every
display to "/ total points", which leaves stored data alone but changes six screens and the PDF.
Not mine because either one changes grades trainees have already been shown.

**2. The completion denominator counts Draft and Unpublished activities.** (medium)
`functions/api/progress.js:10-13` selects `WHERE type = 'Activity'` with no status filter, while
`api/activities.js:78` hides anything not `Published`/`Closed` from trainees and new activities are
created as `Draft`. Three published activities plus two drafts an admin is still writing shows a
trainee who finished all three "3 of 5 completed / 60%", which they can never raise. Adding
`AND status IN ('Published','Closed')` is a one-line change, but it moves the percentage every
trainee and admin currently sees, so it is a decision, not a fix.

**3. `api/leaderboard.js` inflates its completed count the same way bug 1 above was fixed.** (low)
`functions/api/leaderboard.js:37` adds every `activity_id` with no check that the activity still
exists. It shows no percentage, so nothing paints past 100%, but the "activities completed" column
counts archived work. The fix needs a second query for the live activity list, which is a per-request
DB read added to a ranking endpoint — worth doing deliberately rather than as a drive-by.

**4. The AI-review reserve can be claimed by any caller.** (medium)
`functions/_ai-gateway.js:228` sets `review` from the request's own `json` flag, and
`functions/api/sim-ai.js:113` passes `json: !!body.json` straight from the browser. In `admit()`,
`review` makes `open = 1` (line 68), bypassing `AI_REVIEW_RESERVE` — the last 10% the code comment
says is kept so practice chats cannot exhaust it — and skips the `moduleShare` cap entirely
(line 72). A practice-chat page posting `{"json":true}` in a loop keeps being admitted past the 90%
cut-off, and grading and gcal reviews then fail with "The shared AI budget for today is used up".
Not mine because external gateway callers (the CMS, the programs) currently get review treatment
from `json:true` too, so tightening it changes the gateway's published contract.

**5. Progress records are keyed by display name, so same-named trainees merge.** (medium)
`functions/api/program-progress.js:162,171,255` and `progress-records.js:11,33` bucket by
`nameKey()` (lowercased name, batch suffix dropped). Only `username` is unique
(`api/register.js:251`), and `api/ticket-login.js:27` already handles "more than one Portal account
has your name". Two approved trainees both named "Maria Santos" in different batches appear as one
row whose simulator average, run count and portal submissions are both people's results combined —
and the batch CSV exports that merged row. Fixing it means keying on username, which changes the
admin page's grouping and the shape of the archive snapshot.

**6. Username checks are case-sensitive.** (low)
`functions/api/register.js:251,257`, `api/create-user.js:212` and `_utils.js:354` all use
`WHERE username = ?`. No `COLLATE NOCASE` appears in either repo's SQL, and the shared `users` table
is not created by this repo, so the live schema decides. If the collation is BINARY, a permanently
revoked `jsmith` can re-register as `JSmith`, and `api/update-user.js:71`'s username migration moves
only the exact-case rows. Confirm the live collation before changing anything.

**7. KB sessions never re-check Portal revocation.** (medium, cross-repo)
`functions/_utils.js:137-168` re-reads `users.status` on every Portal API call and 401s unless it is
exactly `Approved`. `LSH-Knowledge-Base/src/db.js:146-169` trusts the signed cookie for the full 12
hours, although it holds the same `env.DB` binding and queries that table at sign-in. Revoking a
trainer in the Portal, or their logging out, does not end their Knowledge Base admin session: for up
to 12 hours they keep publish, delete and export rights on the shared library. The site lock
propagates; revocation does not. Either the KB re-checks `users.status` in `getReader`, or the Portal
exposes a revocation endpoint it consults. This one is in both repos' reports.

**8. The heartbeat grace window no longer matches the client interval.** (medium)
`functions/_utils.js:94-106` sets `HEARTBEAT_GRACE_SECONDS = 90` and justifies it with a comment
stating the client interval is 2s and that "3x the nominal interval" was too tight. `app.js:9` sets
`HEARTBEAT_INTERVAL_MS = 30000`, so the shipped numbers are exactly 3×. Background tabs are
throttled to ≥60s, so one throttled beat plus jitter crosses 90s and the session reads as dead —
the intermittent `SESSION_EXPIRED` the comment claims was fixed, and what `api/launch.js:124`
surfaces when a trainee clicks a program from an idle tab (hence the pre-click heartbeat kick at
`programs.html:302`). Raise the grace window or shorten the interval; either touches auth timing.

**9. Three copies of the sign-in card CSS, one unreachable.** (low)
`styles.css:341-366` (pre-dedup), `auth.css:68-100` (shared), and an inline third copy in
`registration.html:13-124` — that page loads `styles.css` and `theme.css` but not `auth.css`. All
three pages using `.auth-*` markup override every one of those rules, so the `styles.css` block is
unreachable: editing the sign-in button in the global stylesheet changes nothing on any page.
Meanwhile registration's inline fork has already diverged in padding, `font-size`, `margin-top` and
the `.auth-submit` colour. Delete the `styles.css` block and point `registration.html` at
`auth.css` — but that is a visual change to the registration page, so it wants an eye on it.

**10. The program→Worker URL map is duplicated and one copy is unreachable.** (low)
`functions/api/launch.js:16-22` (`SSO_PROGRAMS`) and `programs.html:288-294` (`BUILT_PROGRAMS`) hold
the same five keys and URLs, with a third key-only list at `programs.html:299` kept in step by
comment. `programs.html:317` only uses the `built` URL when the key is absent from `SSO_PROGRAMS`,
and all five are present — so changing a Worker URL on the page that lists the programs has no
effect. Reduce the page to the key list or derive it.

**11. Dead code that is deliberately kept.** (low)
`simulators/trainees-calendars.js:65` `window.csFind` and `theme.css:287` `body.no-portal-bg` are
both unreferenced in this repo, and both are documented as deliberate: a legacy global shim an
outside course link may still call, and the README's public opt-out hook for future pages. Unused
API, not accidental — removing either is a call about outside callers.

**12. Configuration that needs confirming, not editing.**
- `wrangler.toml:1` — `name = "case-management-training"`, but the Portal lives at
  `cm-training-activity.pages.dev` (`uptime.mjs:5`) and `case-management-training...workers.dev` is
  a *different* live service (the CM course Worker). CI only builds, so nothing breaks today, but a
  manual `wrangler pages deploy` from this repo would publish the Portal to the wrong project.
  Confirm the real Cloudflare project name.
- `wrangler.toml:2` — `compatibility_date = "2024-03-20"`, two and a half years old. No `node:`
  imports exist, so no compatibility flags are needed; it is a date bump that wants a deploy test.
- `.github/workflows/checks.yml:58` — wrangler pinned to a floating `wrangler@3`, two majors behind,
  and the repo has no `package.json` or lockfile, so this is the only pin. CI can pass against a
  major Cloudflare no longer deploys with.
- jsPDF is split across two majors: CI installs and offline-serves `4.2.1`, `lsh-blueprint.js:323`
  loads `4.2.1`, and eleven pages load `2.5.1` from cdnjs at runtime, version-checked by nothing.
- Eight environment variables are read by code and declared or documented nowhere: `SESSION_SECRET`
  (10 reads; the session-signing secret, so an operator rebuilding the Pages project has nothing
  telling them to set it), the seven `AI_*` budget knobs, `AI_REVIEW_RETRY_MS` and `GEMINI_MODEL`.
  All have in-code fallbacks, so the documented AI budget is whatever the code says, not what the
  dashboard shows. Documenting them is safe and I did not do it this week only because the README's
  secrets are described inline per feature and a consolidated table is an editorial choice.
