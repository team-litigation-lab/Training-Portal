### 2. A Skill Builder shows "Best 100%" after one part, checked twice with the answers it just revealed  — high
Where: `js/pd-skillbuilders.js:113-115` (`scorePart`), `:291-299` (`pdCheckFlags`; the same in `pdCheckSort` `:312-320`,
`pdCheckList` `:331-338` and `pdCheckCalc` `:350-362`); `index.html:9636-9648` (`bumpPracticeProgress`). Read by
`js/pd-practice.js:111`, `index.html:9563,13503,13613,13942`, `worker.js:615` (ranking) and the Portal's `program-progress.js:115`   Category: Bug (scoring)

What happens (plain): each Skill Builder has four parts, such as an audit table, a checklist, a calculator and a written note.
Two things combine:
- **The first check gives the answers away, and the next check counts.** After "Check my calls", every wrong row says
  "✗ Correct call: OK — …" (or "Goes to: …", "Should be selected", "expected $…"). The trainee changes their picks to match,
  clicks Check again, and scores 100%. No attempt is used: the 3-repeat cap (`useLabAttempt`) applies only to the AI-graded
  writing.
- **One part's score is the whole Skill Builder's score.** `scorePart` saves each part's score under the Skill Builder's id
  (`toolOfKey("pdSetup1:flags")` is `"pdSetup1"`), and `bumpPracticeProgress` keeps the maximum. So the best single check of
  any one part becomes the Skill Builder's "best score". Parts the trainee never opened don't count against it.

Steps (verified in the browser, Day 1 · Claim Setup Challenge):
1. Part A (the intake audit table): pick a wrong call on every row and click **Check my calls**. Result: 0%, and each row
   shows its correct call.
2. Pick the calls it showed and click Check again. Result: 100%.
3. Parts B–D are untouched. The Practice page now says **"✓ Best 100%"** for the Claim Setup Challenge, and
   `practiceProgress.pdSetup1` is `{bestScore: 100, runs: 2}`. The trainer's Trainee Audit and scorecard ("best 100%"), the batch
   ranking and the Portal's Practice average all read that number.

Who is hurt: the trainer can't tell from any score who has actually done the Skill Builders. A trainee who really struggled
with the valuation counter shows the same 100% as one who didn't. The trainee also loses the signal: one honest attempt that
scored 60% is overwritten by the copied 100% a minute later.

Fix: proposed (it changes scoring rules). Two independent parts.
```diff
--- a/js/pd-skillbuilders.js
-async function scorePart(key, score){ await bumpPracticeProgress(toolOfKey(key), score); if(score>=90 && typeof burstConfetti==="function") burstConfetti(); }
+// A part's score is its FIRST check (the check shows the answers, so a later one only practises). The Skill Builder's score is
+// the average over all its graded parts, an unattempted part counting 0, so "Best" means the whole exercise.
+async function scorePart(key, score){
+  const tool = toolOfKey(key), pp = (state.practiceProgress = state.practiceProgress || {});
+  const cur = pp[tool] = pp[tool] || {runs:0, bestScore:0, history:[]};
+  cur.parts = cur.parts || {};
+  const first = !(key in cur.parts);
+  if(first) cur.parts[key] = score;
+  const graded = Object.keys(PD_UI).filter(k => toolOfKey(k) === tool);
+  const whole = Math.round(graded.reduce((n, k) => n + (cur.parts[k] || 0), 0) / Math.max(1, graded.length));
+  await bumpPracticeProgress(tool, whole);
+  if(!first) toast("Practice check: your first check of this part is the one that counts.");
+  if(score>=90 && typeof burstConfetti==="function") burstConfetti();
+}
```
`pdGrade` (the AI-graded part) should record `cur.parts[key] = report.totalScore` in the same way. For the reveal, show only
✓/✗ on the first check and the correct call with its "why" from the second check on. That keeps the teaching and drops the
copy. Old records keep their `bestScore` until the trainee's next check. The trainer can use 🔁 reset if a batch is mid-course.

### 3. After the Portal changes a trainee's Batch ID, PD starts them over with an empty record  — medium
Where: `worker.js:505-522` (`traineeSession` looks only at the new batch's ids and the name-only legacy id), `:567-571`
(a new approved record is written); Portal `functions/api/update-user.js:33-37` (an admin changes `batch_id`; course records are
not moved)   Category: Disconnect

What happens (plain): a trainee's PD record is named after their name and batch. When a trainer moves them to another batch on
the Portal (a late start, a repeat, a typo fixed), PD looks for a record under the new batch, doesn't find one, and creates an
empty one. Their Knowledge Checks, Skill Builders and notes stay on the old record, which the trainee can no longer open.
1. Mark Lee signs in under B100126 and passes the Day 1 Knowledge Check (100%).
2. An admin changes his Batch ID to B110226 on the Portal.
3. He opens PD from the Portal. PD signs him in as `mark-lee--b110226`, a new record with `approved: true` and no progress.

Verified (browser): before the change, `{id: "mark-lee--b100126", day 1: 100}`. After the change, `{id: "mark-lee--b110226",
day 1: null}`. The probe also shows both records left in KV, with the progress on the old one.

Side effects (read from code): the old record stays approved and keeps showing in PD's Trainee Audit and ranking as a second
"Mark Lee". If the trainer later revokes his PD access on the Portal, `programBlock` matches the record by name **and** batch
(`_ft-block.js:39,63-66`), so the old record isn't blocked and stays on the lists. Standard Training handles this case
(`movedBatch`, FT audit finding 3), and so does EA / PA (`linkSameName`). PD has neither.

Fix: proposed (it changes which record a trainee gets). Port FT's `movedBatch` idea into `/api/auth/portal`, before
`traineeSession`:
```js
// A trainee whose Batch ID the Portal changed: their record is under the old batch. Keep using it (FT's movedBatch).
async function movedRecord(env, who) {
  const kv = kvOf(env), ids = candidateIds(who.name, who.batch);
  for (const c of new Set([ids.newId, ids.rawId])) if (await kv.get(`trainee:${c}`)) return null;   // nothing moved
  const slug = ids.newId.split("--")[0], hits = [];
  for (const k of (await kv.list({ prefix: `trainee:${slug}--` })).keys.slice(0, 20)) {
    const r = JSON.parse((await kv.get(k.name)) || "null");
    if (r && !r.archived && !r.rejected && slugPart(r.name || "") === slugPart(who.name)) hits.push([k.name.slice(8), r]);
  }
  if (hits.length !== 1 || (await blockedIds(env, true))[hits[0][0]]) return null;   // none, two people, or blocked: no move
  const [id, rec] = hits[0];
  await kv.put(`trainee:${id}`, JSON.stringify(Object.assign(rec, { batchFrom: rec.batch, batch: canonicalBatch(who.batch) || who.batch })));
  await kv.put(`trainee-alias:${ids.newId}`, id);   // so the Portal's call-results / sim-results can follow it (below)
  return id;
}
```
`traineeSession` then needs a `linkedId` argument that it accepts as `chosen`, as EA / PA's does, while keeping the fresh block
check. On the Portal, `call-results.js` and `sim-results.js:28` follow `trainee-alias:` only for EA. Make them follow
`<prefix>trainee-alias:` for every program, or graded calls will land on the new, empty id. The `batchFrom` field is already
read by the Portal's `sameBatch`, so a revoke then matches the moved record too.

### 1. "Review this" on every missed Knowledge Check question takes the trainee to the slide that teaches it  — effort S/M
**What:** after a Knowledge Check, each ❌ question has a button such as "Review: Total loss & ACV (Day 4, slide 18)" that opens

**Why it helps the trainee:** the Answer Review tells a trainee who hasn't passed only "Not quite. Revisit this topic before you

**Where:** add a `t:` (topic index) or `page:` field to each of the 75 questions in `build/day1.js`–`day5.js`. The topics

deck uses (`js/deck-pages.js`).

(README).

### 3. Try again before the answer is shown  — effort S
**What:** the first "Check" marks each row ✓ or ✗ only. The trainee gets one more try on the ✗ rows, and then the correct call
and its reason appear.
**Why it helps the trainee:** the audit tables are the heart of PD: the transposed VIN, the expired dec page, the aftermarket

### 4. Yesterday's misses, re-asked at the start of today  — effort M

**Dependencies:** none. No AI and no new KV family.
